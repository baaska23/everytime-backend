Then you need a polymorphic list shape. Each domain's items (Post, Listing, LostFoundItem) and Ad have different fields, so the response array has to be a tagged union 
  — otherwise the client can't tell a post from an ad.

  Recommended shape:
  // internal/shared/types/entry.go
  type ListEntry struct {
      Kind string `json:"kind"` // "post" | "listing" | "lostfound" | "ad"
      Data any   `json:"data"`
  }

  Ad injection belongs in internal/ads as a helper, so each domain handler calls the same logic:
  // internal/ads/inject.go
  func (s *Service) Interleave(ctx context.Context, items []types.ListEntry, every int) ([]types.ListEntry, error)

  Each handler flow becomes:
  1. Repo returns domain items → wrap each as ListEntry{Kind:"post", Data: post}
  2. adsService.Interleave(entries, 5) inserts ad entries at the right positions
  3. Return via BoringResponse

  This is not FeedItem / FeedSource / internal/feed — it's just a shared wire envelope + one injection helper. No cross-domain aggregation, no interface plumbing. Each   
  domain still owns its own list query and pagination. If you later build a unified home feed, then introduce the FeedSource interface on top of this same ListEntry      
  shape.
